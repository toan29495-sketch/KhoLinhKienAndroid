## Adapter behavior

1. Upload each photo sequentially to `part-images` under the owner/restore-scoped path generated by `RestorePhotoUploadCoordinator`.
2. Use authenticated Storage access and `upsert=true`, so retrying the same restore photo path is idempotent.
3. Download the private object using the current authenticated session.
4. Compare downloaded byte count and SHA-256 with the staged source before returning the `photoEntry -> remotePath` mapping.
5. Never delete the local staged source or remote object. Cleanup is owned by the restore journal only after snapshot commit and Room reconciliation.

## Limits and integration status

- Coordinator enforces a 20 MiB per-photo cap and processes one photo at a time. Verification temporarily holds one downloaded photo in RAM; it does not hold the ZIP or all photos in RAM.
- The adapter/factory are not yet called by `ZipRestore.restore()`. Do not treat this as complete restore-photo integration until chunk staging, restore journal, cloud snapshot commit, and Room reconciliation are connected.
- No Gradle type-check/build or runtime Supabase test has been run.
