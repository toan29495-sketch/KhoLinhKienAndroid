# Step125 – Preserve movement history for deleted parts (2026-11-03)

## Baseline and scope
- Continued from the exact Step124 archive after SHA-256 verification and ZIP integrity validation.
- Audited the complete BACKUP → ZIP staging → cloud payload mapping → SQL commit → immutable snapshot read → Room apply → sync-pull path.
- No Gradle was run or added as a blocker.

## Defect found
- The product explicitly retains movement history after a part/QR code is deleted (`MainActivity` deletion confirmation).
- BACKUP serializes all supplied movement rows, independently storing `code`, `partName`, quantities, reason, machine/store and timestamp. Its manifest records the full movement count.
- RESTORE had two contradictory requirements:
  1. Room `applyCommittedRestoreSnapshot` rejected any movement whose code was absent from the current restored PART catalog.
  2. SQL `commit_inventory_restore` rejected the same valid historical movement and used an inner join to `public.parts`, which would silently omit such rows even if validation were bypassed.
- Therefore a valid backup containing history for a deleted part could not be restored completely.

## Minimal correction
- Room continues to require a nonblank movement code/name, valid transaction type, valid quantity arithmetic, valid timestamp, unique movement UUID and owner-scoped staging. It no longer requires the movement code to exist in the current parts catalog.
- Added migration `202611030013_restore_preserve_deleted_part_history.sql`:
  - Makes `public.movements.part_id` nullable for historical rows whose part is no longer in the current catalog.
  - Replaces `commit_inventory_restore` while preserving authenticated-owner and active-profile checks, all chunk/count/UUID/transaction validations, idempotent commit ledger, owner-scoped replacement, immutable snapshot, cursor and `RESTORE_COMMIT` event behavior.
  - Removes only the movement-to-current-part existence requirement.
  - Uses `LEFT JOIN public.parts` so every validated movement row is inserted; `part_id` is NULL only when the current part no longer exists. The original movement `code` and `part_name` remain intact.
  - Explicitly revokes function privileges from PUBLIC, anon and authenticated before granting EXECUTE only to authenticated.
- Existing movement display and pull mapping use the stored code/name and do not require `part_id`; no permanent photo bytes or other KTV data are touched.
