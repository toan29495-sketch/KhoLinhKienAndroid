# Step126 – Verify normal-sync photo uploads before publishing cloud paths (2026-11-03)

## Baseline and scope
- Continued from the exact Step125 archive after verifying its SHA-256 (`6c1b5f6eeaff371935eb968992fe9f6e30e25931559af0502b41c4e1000aee3c`) and ZIP integrity.
- Audited the photo lifecycle across local pending files, Outbox upload, restore upload, authenticated Storage readback, cloud photo preview cache, backup download, and logout cleanup.
- No Gradle was run or added as a blocker.

## Defect found
- ZIP RESTORE already uploaded each photo and independently downloaded it from private Storage to compare byte count and SHA-256 before creating the mapped `photo_path`.
- Normal KTV Outbox photo sync uploaded the local pending file and immediately returned the cloud `photo_path` based only on the upload response. The database RPC could therefore receive a cloud path without the same explicit readback-integrity check used by RESTORE.
- Although the upload API response and Storage RLS provide useful guarantees, they do not replace an application-level verification that the stored object bytes match the exact local bytes before the database references the object.

## Minimal correction
- Added pure Kotlin/JVM `PhotoIntegrity` helper for SHA-256 and exact byte-count/digest matching.
- Normal Outbox photo upload now reads the pending file once, checks the in-memory byte array remains within 1–20 MiB, hashes those exact bytes, and uploads that exact array.
- After upload, it rechecks the active authenticated owner, downloads the private object through the authenticated Storage session, rechecks the owner again, and requires exact byte count plus SHA-256 match.
- The cloud payload containing `photo_path` is created only after successful readback verification. If upload/readback fails or the account changes, the Outbox operation is not sent to the database RPC; its pending local photo is retained for retry.
- Existing deterministic owner/entity/operation object path, upsert behavior, FIFO Outbox ordering, RPC acknowledgement, and delayed local-file deletion remain unchanged.
- Restore upload's existing readback verification is unchanged.
- Cloud preview images remain in the app cache directory only, bounded to 100 MiB with a 30-day sliding retention policy; logout clears only generated preview-cache files. Original pending files and cloud Storage objects are not deleted by cache cleanup.
